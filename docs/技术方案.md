# FallGuard Harness 技术方案

> 2026 第五届未来杯创新大赛 · 赛道一「Agent 编排创新应用」
> 文档版本：v1.0 · 对应代码 `dc644d8`

---

## 摘要

赛道一要求的不是"一个用了大模型的程序"，而是一套**面向多智能体协作的编排、调度、执行与验证平台**。

我们的判断是：这类平台的核心不在"Agent 能不能聊天"，而在**流程能不能从代码里拿出来、变成可验证的数据**。因此我们把工作重点放在三件事上：

1. **编排表达力**——用 11 种节点原语 + 一张 JSON 工作流图，描述串行、并行、循环、人工介入、条件分支；
2. **可验证性**——15 个带断言的场景，把"系统应该怎么反应"变成可回归的判据；
3. **自我改进**——参数扫描 → 建议 → 采纳 → 写回经验库 → 再验证，形成不依赖人力的闭环。

平台本身不认识任何业务。目前挂了两个**拓扑完全不同、且毫无业务关联**的 pack：

| pack | 拓扑 | 场景 |
|---|---|---|
| 独居老人跌倒响应 | 串行 + 遍历升级链 + 人工撤销窗口 | 15 |
| 多源调研简报 | 并行扇出 + 汇合 + 校验回退 | 2 |

**换领域不改引擎一行**——这是"平台"与"应用"的分界线，也是本文档所有设计取舍的出发点。

## 一、问题定位

### 1.1 为什么选"跌倒响应"做验证场景

平台需要一个能同时暴露四类问题的场景：

- **安全关键**：判定错了会有人身风险，逼出"模型不能进关键路径"的设计；
- **多角色**：分诊、联络、升级职责不同，能体现权限隔离；
- **有时序**：外呼超时、升级链、撤销窗口，能体现动态调度；
- **有外部约束**：用药禁忌会**否决**常规处置，能体现冲突消解。

养老跌倒响应同时满足这四条。它只是**第一个 scenario pack**，不是平台本身。

### 1.2 与"做一个应用"的区别

同样的界面和场景，如果流程写死在 Python 里，换一个领域就要改核心代码——那是应用。
本项目的判断标准很具体：

> **新增一个领域，是否需要改 `harness/` 下的任何文件？**

答案是不需要。加一个目录、写四份 JSON、两个 Python 模块即可（见附录 A）。

## 二、总体架构

```
┌──────────────────────────── 场景包 packs/<id> ────────────────────────────┐
│ pack.json    元信息 / 默认参数 / 可调项 / 记忆策略                          │
│ agents.json  Agent 团队：角色、权限、工具白名单、驱动方式                    │
│ workflows/*.json  工作流图（节点 + 转移）                                   │
│ data/*.json  领域数据（档案 / 规则 / 模型权重 / 已采纳的调优值）              │
│ kb/*.md      文档知识库                                                    │
│ scenarios.json  带断言的验证场景                                           │
│ tools.py / handlers.py  工具与处理器（这里才是业务）                        │
└───────────────────────────────────┬───────────────────────────────────────┘
                                    │  只认这几种文件，不认业务语义
┌───────────────────────────────────▼───────────────────────────────────────┐
│ 编排引擎 harness/engine.py                                                 │
│  input · agent · tool · condition · parallel · foreach · wait              │
│  knowledge · transform · memory · end                                      │
├───────────────────────────────────────────────────────────────────────────┤
│ 支撑层                                                                     │
│  expr.py 受限表达式    trace.py 执行轨迹    knowledge.py 知识源注册中心      │
│  pack.py 加载与缓存    runner.py 统一执行入口  audit.py 静态+动态体检       │
│  lessons.py 经验回写   selfloop.py 参数扫描与采纳                           │
└───────────────────────────────────┬───────────────────────────────────────┘
                                    │
              控制台 harness/server.py + web/index.html
              命令行 harness/cli.py（list / run / validate / audit / dump / learn / tune）
```

**分层的实际意义**：业务逻辑只允许出现在 `packs/*/handlers.py` 和 `packs/*/tools.py`。引擎不 import 任何业务模块，pack 之间互不依赖。

## 三、编排引擎

### 3.1 十一种节点原语

| 原语 | 语义 | 关键字段 |
|---|---|---|
| `input` | 工作流入口 | `next` |
| `agent` | 调用一个已注册 Agent | `agent` `input` `out` |
| `tool` | 调用一个已注册工具（受白名单约束） | `agent` `tool` `args` `out` |
| `condition` | 条件分支 | `when` `then` `else` |
| `parallel` | 并行扇出，全部完成后汇合 | `branches[]` `next` |
| `foreach` | 遍历 + 中断条件（升级链、重试链） | `over` `body` `break_when` `on_break` `on_exhausted` `max` |
| `wait` | 可取消等待（人工确认窗口） | `duration` `on_cancel` `next` |
| `knowledge` | 知识库检索 | `query` `k` `out` |
| `transform` | 写入上下文 | `set{}` `next` |
| `memory` | 跨运行记忆读写 | `op` `key` `out` |
| `end` | 终止并标记最终状态 | `status` |

每个节点还可带 `actor`（写进轨迹，供断言与展示）与 `on_error`（错误转移）。

### 3.2 控制流是数据，不是代码

跌倒响应里的升级链：

```json
"call_loop": {
  "type": "foreach",
  "over": "ctx.triage.contacts",
  "body": "call_one",
  "break_when": "ctx.call.answered or ctx.call.budget_hit",
  "on_break": "gate_call",
  "on_exhausted": "page_community"
}
```

对应旧实现里的一段 Python `for` 循环加 `if`。差别不在写法，在于**换一个拓扑是改数据还是改引擎**。

### 3.3 表达式求值的安全边界

工作流里的 `when` / `args` / `set` 都走同一套表达式语言，实现是 **AST 白名单遍历**，不使用 `eval`：

- 只放行字面量、布尔/比较/算术运算、属性与下标、白名单函数调用；
- 禁止下划线属性（挡掉 `__class__`、`__globals__` 一类逃逸）；
- 禁止赋值、lambda、非白名单调用。

**为什么值得自己写 AST 遍历**：工作流来自配置文件。若直接 `eval`，等于允许配置文件执行任意代码——这在"可配置"的系统里是致命的。校验用例覆盖了 `__import__`、`open()`、`lambda`、属性逃逸等注入形式。

### 3.4 轨迹：把"发生了什么"变成结构化事实

每个节点执行后落一条轨迹，字段固定：`seq / node / type / actor / status / ms / summary`。

`status` 是一等公民，取值 `ok`、`veto`、`cancel`、`error`：

- 断言可以直接查 `trace.veto == 1`；
- 控制台按节点点亮工作流图；
- 复盘时不必翻日志，直接读结构化轨迹。

**把"否决"变成一个可断言的状态**，是本项目最实用的一处设计——护栏不再是一句日志，而是一条可回归的执行事实。

## 四、Agent 团队与权限

### 4.1 权限即白名单，运行时校验

```json
"contact": {
  "name": "联络",
  "driver": "handler",
  "handler": "draft",
  "permissions": ["push"],
  "tools": ["push"]
}
```

调用未授权工具直接抛 `PermissionDenied`，不是靠文档约定。审计器还会静态检查"工具节点是否声明了 agent""agent 白名单里是否真的有这个工具"，把"文档里写了、实际没生效"的情况提前打出来。

### 4.2 冲突消解：一个真实机制，不是演示脚本

跌倒场景里最危险的一句话是"先扶起老人"。服用抗凝药的老人，这句话可能造成二次伤害。

本系统的做法不是让某个 Agent"小心一点"，而是**让它在结构上不可能知道**：

- 联络 Agent 的权限里 **没有 `read_profile`**，它拿不到用药信息；
- 因此它必然给出通用建议（含"先扶起"）；
- Supervisor 的护栏节点读到了禁忌，**否决并剥离**该指令，追加"禁止搬动"警示。

`trace.veto` 记录这次否决。这是权限设计的**后果**，不是编排出来的剧情——这正是安全关键场景需要拆多智能体的实证理由。

### 4.3 LLM 的位置：只做措辞，不进判定

系统里目前只有 `advisor`（家属沟通顾问）声明为 `driver: "llm"`，位置在护栏**之后**：

```
draft → guard → advise → cancel_window → push → ...
```

它拿到的是**结构化结论**（风险等级、搬动禁忌、命中规则、已生成通知），system prompt 明确禁止三件事：做医学诊断、给用药建议、推翻既有处置结论。

**判定链路（核验、分诊、规则匹配、外呼决策）全部是确定性 handler。** 这是刻意的取舍：

> 任何不可回滚的动作、任何涉及人身安全的判断，都不经过模型。

模型的输出如果出错，最坏后果是"话术不自然"，不是"该禁搬动却让人扶起来"。

未配置 `DEEPSEEK_API_KEY` 时自动退回 mock 文本，15 个场景与全部用例不受影响。

## 五、知识库：定义与集成

三种知识源实现同一接口，业务层只依赖 `KnowledgeHub.search()`：

| 知识源 | 作用 | 规模 |
|---|---|---|
| `RuleKnowledge` 规则库 | 决策用，规则引擎读同一份数据 | 6 条 |
| `DocKnowledge` 文档知识库 | 解释用，按 `##` 切片 + 字符二元组检索 | 3 篇 / 9 块 |
| `CaseKnowledge` 经验库 | 复盘结论回写，下一轮分诊可检索 | 动态 |

**刻意不引入向量库。** 理由不是"做不到"，而是三条工程约束：

1. 比赛周期内多一个依赖就多一个现场风险；
2. 召回质量无法用现有 15 个场景客观评价，引入后用不上"更好"的结论；
3. 接口已抽象，后续替换为 embedding 后端只改一个类，不动业务。

这个取舍写在这里，是为了说明**我们知道自己放弃了什么**：当前是字面匹配，语义相近但用词不同的查询会漏召。

## 六、自我循环（Self-Loop）

### 6.1 平台不认参数名，pack 自己声明

```json
"tunable": {
  "ring_scale": {
    "label": "振铃等待缩放系数",
    "candidates": [1.0, 0.95, 0.9, 0.8, 0.6, 0.4, 0.2],
    "goal": "min",
    "metric": "sim_ms"
  }
}
```

平台按 `candidates` 扫描，`goal`/`metric` 决定择优方向。换一个 pack、换一个参数，引擎代码不变。

### 6.2 四步闭环

```bash
python -m harness.cli tune fall-response          # 扫描 + 建议
python -m harness.cli tune fall-response --apply  # 采纳 → 回写 → 再验证
```

1. **扫描**：用每组候选值跑完全部场景，记录通过率与平均仿真耗时；
2. **建议**：在通过率最高的候选里取指标最优；指标并列时优先保留当前值（**避免配置抖动**）；
3. **采纳**：写入 `packs/<id>/data/tuned.json`，由 `Pack.params()` 覆盖默认值——**改数据，不改代码**；
4. **回写**：把结论追加进经验库，下一轮分诊可检索到；
5. **再验证**：用新参数重跑，确认通过率没有下降。

### 6.3 实测：边界是自己撞出来的

把配置故意改坏成 `0.5`，系统自己发现：

| 候选 | 通过 | 平均仿真耗时 | 失败场景 |
|---|---|---|---|
| 0.2 | 8/15 | 3.0s | s1,s3,s5,s6,s7,s9,s13 |
| 0.4 | 9/15 | 5.2s | s1,s3,s6,s7,s9,s13 |
| **0.5（当前）** | **10/15** | **6.2s** | s1,s3,s6,s7,s13 |
| 0.6 | 10/15 | 7.2s | s1,s3,s6,s7,s13 |
| 0.8 | 14/15 | 6.6s | s3 |
| 0.9 | 14/15 | 6.6s | s3 |
| 0.95 | 15/15 | 6.0s | — |
| 1.0 | 15/15 | 6.0s | — |

系统输出：

> 当前取值 0.5 换成 0.95，通过率 10/15 → 15/15，平均仿真耗时 6.2s → 6.0s（节省 0.2s）。
> 再往小走到 0.9 会让 s3 失败，说明这是不能越过的边界。

**边界正好落在 s3——那位服用华法林、家属 12 秒才接听的老人。** 禁忌规则 → 家属接听时间 → 振铃下界，三条线是连着的。

### 6.4 一个不由系统决定的地方

系统推荐 `0.95`（13s × 0.95 = 12.35s），但 s3 家属 12s 接听，**只剩 0.35 秒余量**。

我们的处理是：**不采纳 0.95，保留 1.0 的 1 秒余量，把"0.95 是边界"记进经验库。**

> 系统负责告诉你边界在哪，留多少余量是人的判断。

这条分工是有意保留的：它同时回答了"系统会不会把自己调坏"这个质疑——会做建议，但采纳权在人。

## 七、验证体系

### 7.1 场景即判据

每个场景是一份声明式数据，`expect` 支持四类断言：

| 断言形式 | 含义 |
|---|---|
| `final` | 最终状态 |
| `ctx.<path>` | 上下文取值，如 `ctx.triage.forbid_move` |
| `trace.veto` | 某状态出现次数 |
| `trace.node:<id>` | 某节点执行次数 |

```bash
python -m harness.cli validate fall-response               # 15/15
python -m harness.cli validate fall-response --workflow single   # 4/15（对照组）
python -m harness.cli validate research-brief              # 2/2
```

### 7.2 对照实验

同一个引擎、同一个 pack，两条工作流：

| 工作流 | 通过 | 说明 |
|---|---|---|
| `response`（多智能体） | **15/15** | 核验 → 分诊 → 知识检索 → 护栏 → 撤销窗口 → 推送 → 升级链 → 社区/120 |
| `single`（单 Agent 基线） | 4/15 | 一次决策：直接通知首个联系人，无核验、无规则、无升级、无去重、无护栏 |

基线失败的 11 个场景，失败原因高度集中：

| 缺失能力 | 失败场景 |
|---|---|
| 多信号核验 | s11 手机掉落、s12 语音确认、s13 多信号确认 |
| 情境规则（独居/高龄/夜间/无家属） | s2、s9、s14 |
| 禁忌护栏 | s3 |
| 撤销窗口 | s4 |
| 事件去重 | s8 |
| 置信度闸门 | s15 |
| 推送失败降级 | s10 |

**这张表就是"为什么需要编排"的答案**：不是"多 Agent 更酷"，而是单点决策在 11 类真实情况上会直接失败。

### 7.3 体检（audit）

`validate` 只回答"场景过没过"，`audit` 回答"有没有东西根本没被验证到"：

- 从 entry 不可达的节点；
- 从未被任何场景触发的规则（死规则）；
- 工具节点未声明 agent（白名单形同虚设）；
- 条件节点缺 `else`、`foreach` 缺 `on_exhausted`；
- 结局定义了但没有任何场景走到。

当前结果：

```
pack=fall-response  规则 6/6 被场景覆盖
没有发现问题
```

这条能力是**在补场景时被用上的**：此前只有 13 个场景，`R-NO_FAMILY`（无直系联系人）与 `R-AGE_80`（高龄）两条规则从未被触发，`community_120`、`discarded` 两个结局不可达——也就是说，**文档里写了、代码里有，但没有一条数据证明它生效**。

### 7.4 回归

- 79 个单元测试（`python -m unittest discover -s tests`），覆盖表达式安全、引擎语义、记忆策略、经验回写、LLM 协议层；
- 15 + 2 个场景断言；
- `audit` 静态 + 动态体检。

三者都在 CI 里跑。

## 八、工程实践

### 8.1 统一执行入口

同一件事曾经在三处各写一遍（CLI、控制台、审计），导致控制台跑 s4 不会撤销、跑 s8 不会去重。现在收敛到 `runner.run_scenario()`，三处共用，语义一致。

### 8.2 配置缓存与失效

pack 加载按目录指纹缓存（路径 + mtime + 大小，0.75s TTL），控制台轮询不会反复读盘；经验回写、调优采纳后主动 `clear_cache()`，**不重启服务就能生效**。

### 8.3 部署

- 零第三方依赖，`python:3.12-slim` 镜像直接跑；
- `HOST` / `PORT` 环境变量适配容器；
- `ACCESS_TOKEN` 开启后 `/` 与 `/api/*` 需要令牌（Cookie 或请求头），`/healthz` 公开供探活；
- `MAX_CONCURRENT` 限制并发，超出返回 429；
- 健康检查走 `/healthz`，避免开了令牌后实例被判不健康而反复重启。

## 九、与主流 Agent Harness 的定位差异

赛题建议对标 LobeHub、DeepSeek Harness 等框架。我们**不自称对标**，因为定位不同：

| 维度 | 通用 Agent 框架 | 本项目 |
|---|---|---|
| 首要目标 | 让 Agent 能对话、能调工具 | 让流程**可验证、可回归、可自我改进** |
| 流程定义 | 多为代码内编排 | 数据驱动，pack 自包含 |
| 模型角色 | 核心决策者 | 只做非关键路径的措辞 |
| 质量保证 | 依赖评测集 | 场景断言 + 体检 + 参数扫描 |

我们放弃了通用框架的很多能力（多模型路由、对话管理、插件市场），换来的是**一条能被数据证明的闭环**：改一个参数，15 个场景会告诉你它对不对。

## 十、局限

以下问题真实存在，不做修饰：

1. **判定链路没有用模型。** 核验、分诊、规则匹配、外呼决策都是确定性 handler，只有 `advisor` 走 LLM。这是设计选择（安全关键路径不进模型），但也意味着"多智能体"的智能程度受限于规则表。
2. **没做过真实模型调用。** 协议层已用本地假端点验证（请求头 / 模型名 / 消息体 / 响应解析），但没有真实 key，模型效果、延迟、话术质量未测。
3. **对照组不是独立实现。** `single` 工作流跑在同一引擎上，只换了拓扑与 Agent。它证明"这套编排带来差异"，**不能证明"任何单 Agent 方案都不行"**——这是一个方法学上的局限，写材料时不应夸大。
4. **知识检索是字面匹配。** 语义相近、用词不同的查询会漏召。
5. **审计只覆盖默认工作流。** `single` 的结局不参与体检（此前会结构性误报，已修）。
6. **没有持久化运行记录。** 运行态在内存，重启即丢，做不了历史回放。
7. **场景数据是构造的。** 跌倒的传感器特征（冲击 g 值、失重时长、静止时长、姿态变化）由场景注入，未接真实 IMU；权重与阈值是工程先验，未用现场数据标定。
